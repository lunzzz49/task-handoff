# 交接文档写作标准

判定一份交接文档是否合格的**唯一文件**。SKILL.md 只管流程，这里只管标准。

写好初稿后按「自检七问」逐条打勾，再用 `scripts/handoff.py check` 跑一遍机械校验。

---

## 一、总则：只写新会话推不出来的信息

判断某条该不该写进文档，只问一句：

> **新会话不知道这条，会不会做出一个「能跑但和项目格格不入」的决定？**

会 → 写。不会 → 不写，改成引用路径。

| 该写 | 不该写 |
|---|---|
| 为什么这么选、放弃了哪个方案 | 能从代码直接读出的实现细节 |
| 踩过的坑、试过但失败的路 | 能从 `git log` 看出的提交清单 |
| 用户的偏好与红线（哪些不能动） | 能 `grep` 到的函数签名 / 目录树 |
| 当前环境状态（服务起没起、库有没有数据） | 大段可复制的源码 |
| 验证到哪一步、下一步的意图 | 泛泛的「继续优化」 |

一句话：**能被 `grep`、`git log`、`ls` 得到的信息，用路径引用，不要复述。**

## 二、技术栈与既定契约怎么写

这一节是防止新窗口换语言/换框架的唯一屏障，最容易写成没用的清单。

### 2.1 必须覆盖的四类

| 类别 | 例子 | 为什么必须写 |
|---|---|---|
| 非默认选择 | 「异步任务用 FastAPI `BackgroundTasks`，**故意没用 Celery**」 | 默认选择能从依赖清单看出，非默认选择看不出，新会话会当疏漏去「补全」 |
| 禁区 | 「不要引入新依赖，要加先问」「数据访问一律走 ORM」 | 唯一能挡住换栈/乱引库的东西 |
| 对外契约 | API 路径与字段名、DB 表结构、环境变量名 | 改了会连带炸前端和历史数据，往往不可回滚 |
| 分层职责 | 「`api/` 只做路由，业务在 `services/`」 | 新会话默认会把业务塞进路由文件 |

**不需要写**：语言叫什么、用了什么主流框架——`requirements.txt` / `package.json` 里就有。

### 2.2 版本只记锁定值

写 `Python 3.11`、`Node 20` 这类**确实锁了**的版本。项目没锁就写「版本以 `requirements.txt` 为准」，不要凭记忆填一个版本号——写错比不写更糟。

### 2.3 常驻载体的探测顺序

红线最好放常驻层（每个新会话自动注入），但**载体名字因客户端而异，必须探测项目里实际存在哪个**。

**探测范围**：先看项目根；根下一个都没有，再下探**一层子目录**（`packages/`、`apps/`、各子项目目录）。不再往下探——更深处属于模块内部细节，不是「项目约定」。

| 顺序 | 文件 | 归属 |
|---|---|---|
| 1 | `AGENTS.md` | 跨客户端最通用，多数 agent 客户端都认 |
| 2 | `CODEBUDDY.md` | CodeBuddy（存在时优先于 `AGENTS.md`，后者被忽略） |
| 3 | `CLAUDE.md` | Claude Code 系 |
| 4 | `.cursor/rules/`、`.cursorrules` | Cursor |
| 5 | `.codebuddy/rules/<规则名>/RULE.mdc` | CodeBuddy 结构化规则，需 `alwaysApply: true` 才常驻 |
| 6 | 客户端用户级记忆（如 `~/.workbuddy/memory/*.md`） | ⚠️ 跨所有项目，**不适合**放项目专属技术栈 |

**探到之后先判级别，再决定写在哪**：

| 位置 | 是否常驻 | 写在哪 | 怎么写 |
|---|---|---|---|
| 项目根 | 是，新会话自动注入 | 第 4 节「红线出处」 | 可直接引用，开场 prompt 可提 |
| 一层子目录（如 `my-blog-manager/AGENTS.md`） | **否**，不会被自动加载 | 第 6 节「坑与约束」或第 7 节文件地图 | 必须写明「仅约束某目录，改该目录前先读」 |

子目录级约定**不得写进第 4 节「红线出处」**：那会造成「文档说这是红线，实际那份文件从没进过上下文」的落差，正是下面降级规则要防的情况。

**降级规则**：若目标客户端没有项目级常驻机制（如 WorkBuddy），或约定文件只在子目录，技术栈必须**写全在交接文档里**，不许写「见 xxx 文件」——那份文件不会被加载。此时开场 prompt 必须自带：

> 沿用项目现有技术栈，不要更换语言/框架，不要新增依赖。

### 2.4 常驻规则文件建议骨架

3–5 条就够，越短越容易被遵守（超过 500 行模型的遵守率明显下降）：

```markdown
# 技术栈
- 后端 Python 3.11 + FastAPI，前端 TypeScript + React + Vite。不引入其他后端框架。

# 红线
- 新增依赖前必须先问，不要自行 pip install / npm install。
- 数据访问一律走 ORM，不写裸 SQL 拼接。
- 前端只允许 TypeScript，不新增 .jsx / .js 业务文件。

# 目录职责
- `backend/api/` 只放路由，业务逻辑写 `backend/services/`。
```

规则类文件通常**只在会话开始时注入一次**，改完要新开会话才生效。

### 2.5 判完备性：项目里还有没有别的文档

交接文档不是孤岛，但它能依赖多少外部文档，取决于项目本身有没有。动笔前先判属于哪一档：

| 项目类型 | 典型特征 | 交接文档的角色 | 必须做到 |
|---|---|---|---|
| 有官方文档 | 开源项目、`README.md` + `CONTRIBUTING.md` + `docs/` 齐全 | 补充层：写官方永远不写的隐性契约 | 用法可指路；**必须列出官方文档里哪几节是接手必读的**；不重复用法 |
| 只有零散记录 | 自研项目，有 README 或决策记录但不完整 | 主文档：补齐缺口 | 用法能指到具体文件；**设计理由必须自己写清** |
| 完全没有文档 | 内部项目、脚本堆、私有仓库 | **唯一信息源** | 安装、运行、测试、设计理由全部写全，**不许出现「见某文件」** |

判断依据是项目根与一层子目录里实际存在的载体：`README.md`、`CONTRIBUTING.md`、`docs/`、`docs/DECISIONS.md` 这类决策记录，以及代码文件顶部的说明性注释。有就承认它，没有就别假装有。

判档之后，**第 4 节的写法跟着变**：有官方文档时，「可省略」那组（语言/运行时、框架、分层职责）可以只写指向，不必摘要——摘要一遍既不比原文准，还会随官方文档更新而过期；完全没有文档时两组都要填实，因为没有任何别的地方可查。

**为什么必须分档**：开源项目里「提 PR 要签 CLA」写在官方文档，交接文档抄一遍是浪费版面；但自研项目里没有别的地方写着「为什么这么拆模块」，交接文档不写就永久丢失。同一个模板，在不同项目里该有的详略程度本来就不一样。

**最容易犯的错**：拿开源项目的写法套自研项目，通篇「详见 README」——而那份 README 只有项目名加三行安装命令。

### 2.6 关键决策必须标来源

「决策 / 理由 / 放弃了什么」三列不够用：读的人分不清哪句是项目里真实写着的，哪句是你推出来的。

再加一列**来源**，只填这四种：

| 来源 | 含义 | 可信度 |
|---|---|---|
| `代码注释` | 源文件里明写了理由 | 高 |
| `README` / `docs` | 项目文档明写 | 高 |
| `git log` / `PR` | 提交说明或讨论里写过 | 中高 |
| `推断` | 从代码结构反推的 | **低，必须显式标出** |

标 `推断` 的条目，要么补证据后改标来源，要么降级进「待确认」，不许伪装成既定决策。

开源项目尤其危险：README 只说「不接受 web 服务」，不说为什么；你顺手补的「因为职责发散」是自己的判断，一旦写进表格就变成了项目立场，下一个人会拿它当依据。

## 三、进展条目写法

进度时间线里的每一条，都是将来接手时的证据。写坏一条，代价比不写更大。

### 3.1 一条合格条目

```
- `a2b276` 2026-11-12 14:46 · 完成 CSV 导出并通过验证 · `backend/api/export.py` · 验证：Excel 打开中文不乱码
```

四个成分，缺一不可：

| 成分 | 要求 |
|---|---|
| 做成了什么 | 动词开头，说结果不说过程：「完成 X」「修好 Y」「定位到 Z」 |
| 涉及文件 | 用反引号包相对路径，多个逗号分隔；纯结论可不填 |
| 验证方式 | **必填**，写怎么确认的：「跑通 pytest -k export」「页面点导出能下载」 |
| 时间 | 脚本自动带 |

### 3.2 合格 vs 不合格

| ✅ 合格 | ❌ 不合格 | 问题 |
|---|---|---|
| 修好中文文件名下载失败，`encodeURIComponent` 处理 | 优化了一下导出功能 | 没说做了什么、无法核对 |
| 定位到导出行数 >5000 时前端卡死，因全量渲染 | 排查导出性能问题 | 没给结论，下次还得重查 |
| 补完 xlsx 分支，`pytest -k xlsx` 通过 | 继续完善 Excel 部分 | 空话，且无验证 |

### 3.3 保留原则

- **失败但得出结论的记录比成功的更有价值**——它能阻止下一个会话重走一遍。
- 修完又改回去的，不要删，追加一条「回退 X，因为 Y」，否则新会话看到旧条目会以为还在用。
- 阶段结束时写完整交接，把时间线条目**汇总**进第 2 节「阶段结论」，原始条目保留在附录作为证据链，不要清空。

### 3.4 继承与归档的两条纪律

**继承不等于照抄。** `new --inherit` 搬来的内容带「请核对是否仍然有效」标记，它是上一阶段的快照，可能已经过期。核对后删掉标记行；发现过期的当场改，不要留着当免责声明。

**归档不等于做完。** `summarize --apply` 只把条目搬进归档区，第 2 节「阶段结论」仍然是空的。归档后必须压缩出 3–5 条结论，否则是把历史藏起来，不是提炼。

## 四、自检七问

1. 「下一步第一步」是不是一个新会话**五分钟内就能直接执行**的具体动作？
   - ❌ 「继续完善导出功能」
   - ✅ 「在 `export.py:42` 补 xlsx 分支，跑 `pytest tests/test_export.py -k xlsx`」
2. 有没有密钥、token、密码、真实用户信息？（**只写变量名，绝不写值**）
3. 有没有「上面的」「之前提到的」「那个文件」这类依赖旧上下文的指代？全部换成绝对路径或明确名字。
4. 文档里的路径、命令、**数字**（N 个测试 / N 个模块 / N 个文件）都和现实一致吗？
   - 数字必须现数一遍。`check` 能验路径和结构，**验不了数字**——曾把 19 个测试文件写成 21 个（把 `__init__.py` 算进去了），工具全程 `[ok]`。
5. 技术栈与禁区写全了吗？红线落在项目**实际存在**的那个约定文件上了吗？（一个都没有时，是否已写全在本文件里）
6. 交接文档里提到的路径，下一个客户端读得到吗？（`.handoff/` 是隐藏目录，必要时同时给出绝对路径）
7. 按 2.5 判过项目属于哪一档吗？如果项目没有官方文档，本文件是否真的做到了自包含——随便挑一条命令，新会话照着敲能跑起来吗？

机械项交给 `scripts/handoff.py check`，人判项（第 1、3、4、7 条）只能自己看。

## 五、篇幅界标

| 阶段规模 | 合理篇幅 |
|---|---|
| 单点修复 / 一次排查 | 60–120 行 |
| 一个功能模块 | 150–300 行 |
| 跨多模块的一轮迭代 | 300–400 行，超过就该拆成两份并做索引 |

超出上限通常意味着两件事之一：阶段该拆了，或者你在复述代码。

## 六、反模式

| 反模式 | 后果 |
|---|---|
| 写成日报 / 代码复述 | 新会话读了两千行还是接不上手 |
| 「下一步：继续优化、完善细节」 | 等于没写，新会话只能乱猜 |
| 每阶段全量重写、越写越长 | 文档本身成了负担，最后没人读 |
| 只写在聊天里不给文件 | 关掉窗口就没了 |
| 凭记忆写、不跑 `git status` | 和代码不一致，比没有更糟 |
| 把密钥、真实账号写进文档 | 泄露，且可能被提交 |
| 技术栈只写在交接文档里，不落常驻约定文件 | 新窗口不贴文档时照样被换栈、乱引库 |
| 技术栈一节堆满依赖清单里已有的库名 | 占篇幅、易过期，真正该写的「禁区」反而漏掉 |
| 同一份文档里「已完成」和「下一步」互相矛盾 | 新会话无法判断该信哪句 |
| 静默追加进展、不报 ID | 用户想撤也撤不回来 |
| 把没验证的改动记成「已完成」 | 假账，下一个会话会基于它做判断 |
| 只探项目根就断言「无常驻规则」 | monorepo 的真实约束全在子项目目录里，等于漏掉一层 |
| 把子目录级约定升级为全局红线 | 新会话以为有常驻保护，实际文件从未被加载；或把某模块的规则套到别的模块 |
