# 交接文档模板

本文件只负责「长什么样」。什么算合格（自检七问、篇幅界标、反模式）见 `standards.md`。

骨架的唯一来源就是下面这个块——`scripts/handoff.py new` 会直接抽取它生成文件。

---

## 骨架

````markdown
# 交接：<阶段主题>

- 生成时间：YYYY-MM-DD HH:mm
- 项目：<项目名>（<项目根绝对路径>）
- 分支：<git 分支名，非 git 项目写「无」>
- 覆盖范围：<从哪个任务/提交开始> → <到哪个任务/提交结束>
- 上一份交接：<路径，或「无」>
- 状态：<已完成 / 进行中 / 阻塞>

## 1. 一句话目标

<这个项目/阶段要解决的问题，一到两句。写给人看，不写技术栈堆砌。>

## 2. 阶段结论

<这一段交付了什么，逐条列。每条尽量带可验证的产物：文件路径、接口、页面、通过的测试。>

- ...
- ...

## 3. 当前状态

**整体**：<可运行 / 半成品 / 阻塞>

**运行态**
- <服务是否在跑、跑在哪个端口、由谁启动（用户手动启动 / 脚本）>
- <数据库/缓存里有没有数据、是否需要先初始化>

**代码态**
- 未提交改动：<`git status` 的摘要，或「干净」>
- 临时文件/调试代码：<路径，或「无」>
- 已知未修的瑕疵：<...>

## 4. 技术栈与既定契约

> 只写「新会话不知道就会跑偏」的部分。能从依赖清单或常驻约定文件读出来的，指路即可，不要复述。
> 常驻红线应放在项目根**实际存在**的 agent 约定文件里（见 `standards.md` 第 2.3 节探测表）。这里只写本阶段新增/变更的约束。
> 若目标客户端没有这类常驻机制，则本节必须写全，不能留「见某文件」。
> 两张表的分工是硬要求：第一张缺了会跑偏，第二张缺了顶多多查一次文件。项目有官方文档时第二张可以直接写指向，不要为了填满而把官方文档摘要一遍。

**必须自己写**（官方文档与依赖清单里都不会有，缺了就会跑偏）：

| 项 | 内容 | 是否可动 |
|---|---|---|
| 非默认选择 | <例：异步任务用 BackgroundTasks，故意没用 Celery> | 保持现状 |
| 禁区 | <不要引入新依赖 / 不写裸 SQL / 前端只允许 TS> | 硬红线 |
| 对外契约 | <API 路径与字段名、DB 表、环境变量名> | 改动需同步前端 |

**可省略**（能读到就别抄，写指向即可；项目没有官方文档时仍要填实）：

| 项 | 内容 | 是否可动 |
|---|---|---|
| 语言/运行时 | <Python 3.11，或「见仓库依赖清单的 requires-python」> | 不可动 |
| 框架 | <FastAPI + React + Vite，或「见依赖清单」> | 不可动 |
| 分层职责 | <`api/` 只做路由，业务在 `services/`> | 保持现状 |

**红线出处**：<项目根实际存在的约定文件路径，如 `AGENTS.md` / `CODEBUDDY.md` / `CLAUDE.md`；一个都没有时写「无常驻规则文件，红线仅记录在本文件」>

## 5. 关键决策

| 决策 | 理由 | 放弃了什么 | 来源 |
|---|---|---|---|
| <选了什么> | <为什么> | <被否掉的方案及原因> | <代码注释 / README / git log / 推断> |

> 这一节的目的是防止新会话把你已经否掉的方案重新提一遍。凡是有「我们试过不行」的部分，必须写进来。
> 「来源」列不能空。「推断」可以写，但要让人一眼看出那是你的判断，不是项目立场——判定标准见 `standards.md` 2.6。

## 6. 坑与约束

**踩过的坑**
- <现象 → 原因 → 正确做法>

**约束与红线**
- <不许动的文件/目录>
- <用户的偏好，例：服务由用户自己启动，不要代为重启>

## 7. 文件地图

| 路径 | 作用 | 本阶段 |
|---|---|---|
| `<相对路径>` | <一句话> | 新增 / 改动 / 只读参考 |

> 只列**接手时绕不开**的文件，10 个以内。全量目录树没有价值。
> 项目有官方文档时（判定见 `standards.md` 2.5），在「本阶段」列注明哪几节必读，例如「只读，必读第 3 节插件机制」——不展开内容，但要让人知道去哪看。
> 项目没有官方文档时，这一表就是唯一的入口，作用一栏要写到「点开就知道干什么」的程度。

## 8. 验证方法

**启动**
- 命令：<...>
- 端口/入口：<...>

**确认成功**
- <可观察的判据：日志出现什么、页面看到什么、接口返回什么>

**上次验证结果**
- <命令 + 结果 + 时间点；没验证的写「未验证」>

## 9. 下一步

**优先级**
1. <最高优先级任务，说明为什么它最优先>
2. ...
3. ...

**第一步动作**
> <具体到一个文件/函数/命令。新会话读完这句就能立刻动手。>

**待确认**
- <需要用户拍板的问题，带选项>

## 10. 接手方式

新窗口开场直接粘贴：

```
读 <本文件绝对路径>，按第 9 节「第一步动作」继续。
先跑 git status 和文中的验证命令核对现实，与文档不一致时以代码为准并告诉我。
沿用项目现有技术栈，不要更换语言/框架，不要新增依赖。
```

建议下一个会话调用的技能：<skill 名，或「无」>
````

## 填好的例子（仅示范写法和颗粒度）

````markdown
# 交接：用户导出功能（Excel + CSV）

- 生成时间：2026-11-12 21:30
- 项目：SmartVoyage（d:/Projects/SmartVoyage）
- 分支：feature/export
- 覆盖范围：从「导出需求确认」到「CSV 分支跑通，Excel 分支未完成」
- 上一份交接：无
- 状态：进行中

## 1. 一句话目标

让用户在行程详情页把行程导出成 Excel/CSV，方便离线发给客户。

## 2. 阶段结论

- `backend/api/export.py` 新增导出端点，CSV 分支已验证可用
- 前端详情页加了「导出」下拉菜单（`frontend/src/components/ExportMenu.tsx`）
- CSV 中文表头乱码已修复（加了 utf-8-sig BOM）

## 3. 当前状态

**整体**：半成品，CSV 可用，Excel 未实现

**运行态**
- 后端由用户在自己 cmd 里启动，端口 8000；本次会话没重启过，改完代码后**需要重启才生效**
- 数据库已有 3 条测试行程数据（id 1-3）

**代码态**
- 未提交改动：`backend/api/export.py`(新)、`frontend/src/components/ExportMenu.tsx`(新)、`frontend/src/pages/TripDetail.tsx`(改)
- 临时文件：`backend/test_export_tmp.py` 是调试脚本，可直接删
- 已知瑕疵：导出行数超过 5000 时前端会卡（未处理，不做也行）

## 4. 技术栈与既定契约

| 项 | 内容 | 是否可动 |
|---|---|---|
| 语言/运行时 | Python 3.11（`requirements.txt` 未锁版本）+ Node 20 | 不可动 |
| 框架 | 后端 FastAPI，前端 TypeScript + React + Vite | 不可动 |
| 非默认选择 | 异步任务用 FastAPI `BackgroundTasks`，故意没引 Celery | 保持现状 |
| 禁区 | 不新增后端依赖（openpyxl 已有）；前端只写 `.tsx`；不写裸 SQL | 硬红线 |
| 对外契约 | `GET /api/trips/{id}/export?format=csv\|xlsx`，路径与参数名已告知前端，不要改 | 改动需同步前端 |
| 分层职责 | `backend/api/` 只做路由与参数校验，逻辑写 `backend/services/` | 保持现状 |

**红线出处**：项目根无任何 agent 约定文件，以上红线仅记录在本文件，建议下次会话补建 `AGENTS.md`（跨客户端通用）。

## 5. 关键决策

| 决策 | 理由 | 放弃了什么 | 来源 |
|---|---|---|---|
| 后端生成文件、前端直接下载 | 数据量可能大，避免在前端拼装内存暴涨 | 前端用 SheetJS 本地生成（简单但大数据会卡死浏览器） | 代码注释 |
| CSV 用 utf-8-sig | 否则 Windows Excel 打开中文乱码 | 纯 utf-8（Mac 正常，Windows 乱码） | 代码注释 |
| Excel 用 openpyxl 而非 xlsxwriter | 项目已有 openpyxl 依赖，不想加新包 | xlsxwriter（性能更好，但多一个依赖） | 推断：依赖清单里没 xlsxwriter，推测是为省依赖 |

## 6. 坑与约束

**踩过的坑**
- Windows Excel 打开 CSV 中文乱码 → 编码必须 `utf-8-sig`，不要改成 `utf-8`
- 前端 `blob` 下载时若 `Content-Disposition` 里带中文文件名，需 `encodeURIComponent`，否则下载失败且无提示

**约束与红线**
- 不要改 `backend/models/` 下任何文件
- 服务由用户自己在 cmd 启动，不要代为启动或重启

## 7. 文件地图

| 路径 | 作用 | 本阶段 |
|---|---|---|
| `backend/api/export.py` | 导出端点，CSV 已实现，Excel 待补 | 新增 |
| `frontend/src/components/ExportMenu.tsx` | 导出下拉菜单 | 新增 |
| `backend/requirements.txt` | 依赖清单 | 未改，Excel 实现无需新增依赖 |

## 8. 验证方法

**启动**（用户自己在 cmd 执行）
- 后端：`uvicorn backend.main:app --port 8000`
- 前端：`npm run dev`

**确认成功**
- 打开行程详情页 → 点「导出」→ 选 CSV → 浏览器下载出文件 → Excel 打开中文不乱码

**上次验证结果**
- 2026-11-12 21:10，CSV 分支下载 + 中文正常，已验证
- Excel 分支：未实现，未验证

## 9. 下一步

**优先级**
1. 补 Excel 分支（用户明确要的功能，CSV 只是顺带）
2. 补导出按钮的 loading 态（现在点了没反应，用户以为没生效）

**第一步动作**
> 在 `backend/api/export.py` 的 `export_trip()` 里补 `format == "xlsx"` 分支：用 `openpyxl.Workbook()` 写行，`Response` 的 media_type 设 `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`。改完让用户重启后端，再验一次下载。

**待确认**
- 导出行数上限要不要做到 5000 以上？（涉及改成分页流式写入，工作量 +2h）

沿用项目现有技术栈，不要更换语言/框架，不要新增依赖。
```

建议下一个会话调用的技能：无
````
